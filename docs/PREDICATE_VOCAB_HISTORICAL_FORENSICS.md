# Predicate vocabulary — historical forensics (Part B/C follow-up)

This supersedes the confidence level (not the underlying facts) of
`docs/PREDICATE_VOCAB_INDEX_BUG_TRIAGE.md`. That document found the
*current* `vocabulary/predicates.json` diverges from `STANDARD_VG150_PREDICATES`
and speculated this was the likely cause of Experiment A's collapse, with
an explicit caveat that the true historical training-time order was
unrecoverable. **It has now been recovered, directly, from a second
artifact in the same recovery — not inferred.**

## The direct evidence

`checkpoints/demo_best/frequency_prior.json` was recovered *alongside* the
checkpoint (same mtime, same historical GCP run). `tools/build_vg150_frequency_prior.py`
resolves its `predicate_vocab` field via `scan_vg150_predicate_vocab(vg150_root)`
(`build_vg150_frequency_prior.py:29-33`) — the **same function** `eval_sgg_standard`
calls to build the classifier's label vocabulary (`evals.py:1350`). Whatever
order this artifact recorded is, with high plausibility, the order the
historical environment's `vg150_root` actually resolved to.

Its `predicate_vocab` (50 entries, printed in full):

```
above, across, against, along, and, at, attached to, behind, belonging to,
between, carrying, covered in, covering, eating, flying in, for, from,
hanging from, has, holding, in, in front of, laying on, looking at,
lying on, made of, mounted on, near, next to, of, on, on back of, over,
painted on, parked on, part of, playing, riding, sitting on, standing on,
to, under, using, walking in, walking on, watching, wearing, wears, with
```

This is **exactly `sorted(STANDARD_VG150_PREDICATES)`** — it includes
`"next to"` (index 28) and `"wrapped around"` (index 49), and excludes
`"growing on"` and `"says"` entirely. It does **not** match the current
`datasets_vg150_clean/vocabulary/predicates.json` (which has `"growing on"`
at index 17 and `"says"` at index 38, and lacks both `"next to"` and
`"wrapped around"`).

**Sanity check** (not just a formatting coincidence): ranking this
vocabulary's `global_log_probs` by frequency reproduces exactly the
well-known VG150 predicate distribution — `"on"` is the single most
frequent predicate (36.5% marginal probability), followed by
`has`/`in`/`of`/`wearing`; the rarest is `"flying in"` (0.07%). This is
internally consistent with real, correctly-labeled VG150 statistics under
this vocabulary — strong circumstantial confirmation this artifact
reflects genuine historical data, not a corrupted or placeholder file.

**Revised confidence**: `docs/PREDICATE_VOCAB_INDEX_BUG_TRIAGE.md`'s cause
B is upgraded from "high confidence, partially inferred" to **"very high
confidence, directly corroborated by a second historical artifact from
the same recovered run."** The current `vocabulary/predicates.json` is
very likely genuinely incompatible with what this checkpoint's classifier
head was trained against.

## The one puzzle this does *not* resolve

`"on"` sits at **index 30 in both** the current (wrong) vocabulary and the
`frequency_prior.json`-implied historical vocabulary — the shifted range
from `"growing on"`'s insertion runs from index 17 through the low 40s
(see the full index table in `PREDICATE_VOCAB_INDEX_BUG_TRIAGE.md`), and
index 30 falls outside it. If the classifier's true training-time index
order is exactly the `frequency_prior.json`-implied order, and the current
vocabulary agrees with it at index 30, then a correctly-loaded, genuinely
capable classifier's confident "index 30" output should still have been
labeled `"on"` correctly in Experiment A — yet `"on"` never appeared in
that run's top-8 predictions at all.

Two explanations remain open, **neither confirmed**:

1. **The frequency-prior artifact's vocab order does not exactly equal the
   classifier's training-time order** — they are generated by different
   tools (`build_vg150_frequency_prior.py` vs. `train.py`'s own vocab
   resolution), and although both call the same `scan_vg150_predicate_vocab`
   function, they were not proven to be invoked against byte-identical
   `vg150_root` states at the exact moments each artifact was produced.
2. **A second, independent contributing factor** — this checkpoint's
   embedded config shows aggressive long-tail-oriented training choices
   (`predicate_ce_loss='focal'`, `predicate_ce_gamma=1.5`,
   `predicate_background_weight=0.1`, `predicate_ce_max_weight=5.0`,
   `predicate_ce_weight_power=0.5`) explicitly designed to counteract
   head-class dominance. Evaluated **raw** (Experiment A's deliberate
   choice: no calibration, no ensemble, no frequency bias — exactly the
   `demo_config.env` overlays this checkpoint's "best" reported number
   used), a model trained with this kind of aggressive reweighting could
   plausibly show tail-skewed behavior that its calibration layer is
   specifically meant to correct. This is a **plausible, not verified,**
   alternative/contributing explanation, and — if true — would mean part
   of Experiment A's collapse is by-design "raw" behavior, not a bug at
   all.

**This is exactly the kind of thing a small, cheap, corrected-vocab
verification run (not executed in this phase, per the constraint on
expensive evaluation) would resolve directly** — see
`docs/HISTORICAL_CHECKPOINT_DIAGNOSTIC.md` and `PROJECT_STATUS.md` for
this as the recommended next step. Not run here.

## Frequency-prior schema (Part C)

- **Predicate identity**: encoded **positionally** (array index into a
  50-length float array), matching `predicate_vocab`'s order — no explicit
  numeric predicate ID field exists anywhere in the file.
- **Subject/object identity**: encoded as **raw lowercase label strings**,
  not IDs — `pair_log_probs` keys look like `"a dark shelf||microwave"`
  (subject and object joined by `||`); `subject_log_probs`/`object_log_probs`
  are keyed by the bare label string. These are **free-text, pre-canonicalization
  labels** (25,918 distinct object-label strings per `stats.num_object_labels`
  — not the 150-word canonical VG150 object vocabulary), consistent with
  being built directly from raw annotation text rather than a canonicalized
  object-class ID space.
- **Does the prior correspond to the same dataset preprocessing as
  `datasets_vg150_clean`?** No — `stats.num_relationships=251,126` does not
  match this session's freshly-prepared `datasets_vg150_clean/train.jsonl`
  (1,046,427 relationships). It was built from the original GCP run's own
  `datasets/train.jsonl`, which no longer exists on this machine.
- **Can it independently validate the historical predicate-class mapping?**
  Yes — this is precisely what this document uses it for above, and it is
  the strongest available evidence on this question given the original
  `datasets/` root is gone.
- **File not modified** — read-only inspection throughout, per instructions.
